# 2026-10-16 VPS 验证

本轮在承载业务的 xtom JP 上验证 v2.3.0，HK 与 ISIF JP 作为受控目标。没有重启代理服务、替换 qdisc、安装内核或写入 `/etc/sysctl.d`。为测试加载了发行版已有的 `tcp_bbr` 模块；系统默认参数在每次会话后恢复。

被测 `tcptune.sh` 的 SHA256：

```text
aee6a003ae3c9f4b0ed3993e69c9d6f0052e064c9b51a796be7f184fb7c2ff01
```

测试输入是规范 LF 的源码副本，没有 `.git`，原报告的 `commit=unknown`；因此按脚本哈希核对版本。xtom 内核为 `6.19.14+kali-cloud-amd64`，客户端 iperf3 为 3.12，HK 服务端为 3.12，ISIF 服务端为 3.19.1。初始默认 CUBIC / fq_codel；业务进程为 xboard-node，约 1 GiB 内存。这不是高并发压力测试。

## 实际测到了什么

以下为接收端吞吐中位数。单连接诊断使用 `-C cubic/bbr -b 0 -t 10`，每条路径三对 AB / BA / AB，间隔三秒，仅改变测试 socket 的 CC。

| 路径 | CUBIC Mbps | BBR Mbps | 说明 |
| --- | ---: | ---: | --- |
| xtom → HK | 5.48 | 215.94 | 该时段该路径存在明显差异 |
| xtom → ISIF | 998.29 | 998.17 | 接近链路上限，吞吐无改善 |

第一次 HK 探测使用 128 MiB 字节额度，25 秒截止时仅发送约 12.1 MB，被终止并保留为失败记录，没有当作完整性能样本。

随后运行未修改阈值的真实自动流程，均未配置代理探针或 `--proxy-service`：

| 会话 | 参数 | 独立验收 | 结果 |
| --- | --- | --- | --- |
| HK-timed | 10 秒，1000 Mbps 上限，五对复测＋全新三对验收 | 接收吞吐中位数 3.80 → 180.56 Mbps；配对收益中位数 +4571.77%；每对均通过重传、延迟保护 | `validated`，恢复确认 |
| ISIF-byte | 不限速，每轮 768 MiB，至少五秒，三对复测＋全新三对验收 | 接收吞吐 998.50 → 996.91 Mbps，配对吞吐收益 -0.08%；负载下发送者平均 TCP RTT 中位数 10.695 → 6.213 ms，配对延迟改善 +41.91% | 延迟分支 `validated`，恢复确认 |
| ISIF-receive | `upload` / iperf `-R`，五秒，1000 Mbps 上限 | 仅测基线，约 974.77 Mbps；没有可作用于远端发送者的本机 CC 候选，未进入独立验收 | `no_change`，`acceptance=null` |

独立验收使用了全新数据，未通过多次重跑筛选“好看”的成功结果。HK 的不限速单连接诊断与正式流程发生在不同时间，且后者有 1000 Mbps 上限，因此应分别看待其数值。配对收益中位数也不等同于两个吞吐中位数相除。

ISIF 的改善指标是**负载下测试 TCP 连接的平均 RTT**，不是 ping、代理小请求 P95 或国内客户端延迟。接收方向未取得发送者 RTT 时保留 `null`。

## 数据与恢复核验

[summary.json](summary.json) 保存去除服务器地址、主机名和会话路径后的逐轮数值，包含 12 个单连接诊断样本、33 个正式测量样本、失败发现样本、复测与独立验收统计、原始文件 SHA256。它们是实测记录，不是 `tests/` 的合成数据，也不是完整原始报告。

原始 iperf JSON、stderr、socket 诊断、会话报告和快照已私下留存，公开仓库不包含服务器登录信息。逐条从原始 iperf 输出重新核对了接收吞吐、接收字节和两端较大的发送载荷；三次会话的载荷账本均能对回原始数据。原始证据压缩包的 SHA256：

```text
单连接诊断 a36833760cdb391e89da770cfdf0a85ac01d1b719a85e783430e15ed3d8067c9
自动会话   700a6bd142e2ed562421d150f5f123bb6cf5a5345ae38b7999585e9f5457fb67
```

计入失败发现样本，本轮唯一传输的应用层载荷约 20.86 GiB；不含重传字节、包头、ACK、SSH 和准备流量，不能作为运营商账单。运营商也可能对两台 VPS 分别计费。

会话结束后，三台机器保存的六项 sysctl、完整 qdisc JSON、`/etc/sysctl.d` 文件哈希，以及代理进程 PID / 启动 tick 均与各自测试前一致。临时 iperf 监听和仅保护测试端口的防火墙表已清理。BBR 模块保持已加载；未强制卸载或中断可能引用它的连接。

另在 xtom 上执行真实参数应用、读回及 `persist_final_atomic`，配置文件使用实验目录内的私有路径，验证保留其他条目、原子保存与恢复成功；没有把该文件配置为开机加载。它不能代替 `/etc/sysctl.d` 启动顺序或重启验证。

恢复默认参数不会改变试验期间已创建业务 socket 的 CC；已有监听 socket 也可能继续使用原 CC。这一限制已保留在主 README 中，不能把默认参数恢复等同于所有业务连接完全回到原状态。

## 自动测试与合入边界

Linux / jq 1.6 验证：100 项回归断言、66 项测量断言、16 项本机代理断言、16 项报告断言、23 项菜单断言、109 项流程断言、16 项真实进程断言，共 346 项通过。Bash 语法和 diff 检查通过。

Python 在 Linux 运行 13 项，12 项通过、1 项 Windows 专用测试跳过；Windows 13 项全部通过。包含真实子进程超时、父进程提前退出、桥接关闭及 Windows Job 分配失败的拒绝路径。内核状态测试仍使用假 sysctl/tc 后端，本机代理测试使用真实 curl 和回环 HTTP/SOCKS，不产生公网性能证据。

这些结果支持将当前版本作为**保守试验工具**通过 PR 合入 main；它们不支持宣称所有线路提速、国内 VLESS 体验已验收或重启持久化已验证。上述三份正式报告均为 `proxy_experience=not_verified`、`reboot_verified=false`。真实国内客户端及不同时间段仍需分别测量。
